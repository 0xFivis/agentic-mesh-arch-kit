## 1. SSOT 三层位置

| 层 | 范围 | 寿命 | 物理位置 | 角色 |
|---|---|---|---|---|
| **L1 per-feature** | 单个需求 | 短，feature 结束归档 | 消费仓 `specs/NNN-<feature>/` | SPEC（工作底稿）|
| **L2 per-service** | 单个服务 | 长，服务生命周期 | [`docs/services/<svc>/`](../services/) | 3 强制 + 4 按需 + 1 自动（SSOT/VIEW/AUTO 混合，靠 ROLE 徽章区分）|
| **L3 全局 SSOT** | 跨服务 / 平台级 | 长 | [`contracts/`](../../../contracts/) + [`docs/architecture/`](.) + [`docs/adr/`](../adr/) + [`tech-standards/`](../../tech-standards/) + 消费仓 `apps/<svc>/migrations/` | 不变量 / 契约 / 决策 / 标准 / schema |

**核心断言**：L1 寿命短，L2/L3 寿命长；L1 必须**回写** L2/L3（详 §4 与 playbook §3.7），否则下一 feature 漂移。

**SSOT 红线（不可破）**：

1. **VIEW 文件禁止复制 SSOT 的 schema / 枚举 / 字段定义** —— 只能用 markdown 链接引用源
2. **全平台一致的信息必须放 `tech-standards/`** —— 错误码 / 鉴权矩阵 / 幂等模式 / SLO 等级 / 数据分级 等不下放到 service VIEW
3. **`_data-index.md` 头部 `AUTO-GENERATED, DO NOT EDIT`** —— 人改即漂移；由 `scripts/build-data-index.py` 生成

**ROLE 徽章**（D19，每个 `.tmpl` 与生成的 `.md` 第一行注释之后）：

```
<!-- ROLE: SSOT | source-of-truth for ${topic} -->
<!-- ROLE: VIEW | derived from ${ssot-path}, narrative only, no schema duplication -->
<!-- ROLE: SPEC | per-feature draft, sync back to ${target} at ${stage} -->
<!-- ROLE: AUTO | machine-generated by ${script}, DO NOT EDIT -->
```

## 2. STD 演进流程

`tech-standards/STD-NN-<topic>.md` 是全平台横切规范的 SSOT。

| 阶段 | 触发 | 产物 | 审批 |
|---|---|---|---|
| 提案 | 横切问题反复出现（≥2 服务同样的坑）或合规要求 | `tech-standards/_proposals/STD-NN-<topic>-draft.md` | 提案人 |
| 评审 | 提案 ≥ 5 工作日 | 评审记录 + 修订版 | 架构组 + 受影响服务 TL |
| 发布 | 评审通过 | `tech-standards/STD-NN-<topic>.md` + CHANGELOG 一行 | 标准组 sign-off |
| 季度复核 | 每季度 §6 节奏 | 复核报告（保留/修订/废弃）| 标准组 |

**红线**：

- STD 用「**必须 / 不得 / 应当**」三档措辞；模糊词（"建议、可以"）退回
- STD 变更**必须**给 30 天迁移窗口 + CI 兜底（不允许"立即生效"）
- STD 之间不互相引用业务细节（业务规则属 ADR / architecture，不属 STD）

## 3. ADR 演进流程

`docs/adr/ADR-NNNN-<title>.md` 是在 N 个候选里**为什么选 X** 的决策记录。

| 状态 | 含义 | 转移条件 |
|---|---|---|
| `proposed` | 草案，有候选 + 对比 | 写入对比矩阵 + ≥ 2 候选 |
| `accepted` | 通过评审 | 架构组 + 相关 TL approve |
| `superseded by ADR-NNNN` | 被新 ADR 取代 | 新 ADR 必须显式 supersede 链接 |
| `deprecated` | 不再适用但无替代 | 标 deprecation 日期 + 原因 |

**红线**：

- ADR **不删**只标 superseded / deprecated（决策链可追溯）
- ADR 候选 ≥ 2 且必须含「不选 X 的理由」
- ADR 与 STD 的边界：**ADR 回答"为什么选"，STD 回答"必须怎么写"**；同一主题先 ADR 后 STD（ADR 是 STD 的依据）

## 4. 架构事实演进

`docs/architecture/00-08*.md` + `docs/architecture/_context-map.yaml` 是平台架构事实的 SSOT。

| 文档 | 何时改 | 触发 |
|---|---|---|
| `_context-map.yaml` | 新增 / 拆分 / 合并 BC | feature 涉及新 BC → T1 影响分析阶段 |
| `01_业务上下文与限界上下文` | BC 边界变化 | 同上 |
| `02_系统全景架构` | 服务拓扑 / 数据流变化 | 新服务上线 / 服务退役 / 跨 BC 集成模式变化 |
| `03_微服务拆分原则` | 拆分规则变化 | ADR 决议变化拆分原则 |
| `04_数据架构` | 主存 / 复制 / 一致性策略变化 | ADR-NNNN 决议变化 |
| `05_多主体与合规架构` | 合规口径变化 | 法规更新 / 新增主体 |
| `06_集成与外部边界` | 外部依赖增减 | 新增 / 替换 / 下线外部系统 |
| `07_跨上下文协作模式` | 协作模式变化（saga/事件/同步调用） | T2 详设引入新模式 |
| `08_技术选型与 ADR 索引` | 任意 ADR 状态变化 | ADR accepted/superseded |

**回写时机**：T1 草案 → T2 锁定 → T7 收尾（参 playbook §3.7 ④）。

## 5. 新服务接入流程

> 与 playbook §3.6 附表「特殊 task · 新建服务类 task」是同一流程的两份视图；本节是 arch-kit 这一侧的权威细则。

**3 步**（必须按顺序）：

1. **bctx 注册** —— 服务必须挂在 `_context-map.yaml` 已登记的 bctx 下。新 bctx 走 ADR + 更新 `_context-map.yaml` 与 `01_业务上下文`。
2. **跑 `scripts/new-service.sh --type <api|worker|saga|gateway> --name <short> --bctx <bctx>`** —— 实例化 `apps/<svc>/` 骨架 + `contracts/<bctx>/` 骨架 + `docs/services/<svc>/` 文件矩阵（详 §5.2）。
3. **基于 spec.md 填强制文件草稿** —— 至少 README + runbook + non-functional；按类型加 4 按需文件之一/多个。

### 5.1 ROLE 徽章规则

每个 `docs/services/<svc>/*.md` 首行注释必须含 `<!-- ROLE: ... -->`（参 §1）。模板已预填，作者改 `${topic}` 等占位。

### 5.2 文件矩阵（D14-16）

| 类型 | README | runbook | non-functional | api | events | saga | state-machine | _data-index |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| **api** | ✅ | ✅ | ✅ | ✅ | ✅ | — | — | AUTO |
| **worker** | ✅ | ✅ | ✅ | — | ✅ | — | ✅ | AUTO |
| **saga** | ✅ | ✅ | ✅ | — | ✅ | ✅ | ✅ | AUTO |
| **gateway** | ✅ | ✅ | ✅ | ✅ | — | — | — | AUTO |

- 3 列**强制**：README / runbook / non-functional
- 4 列**按需**（由 `--type` 自动选）：api / events / saga / state-machine
- 1 列**自动**：`_data-index.md` 由 `scripts/build-data-index.py` 扫 `apps/<svc>/migrations/` 生成
- **不再生成**：`data-model.md`（被 `migrations/*.sql` + `_data-index.md` 取代）/ `open-questions.md`（用 Issue tracker 取代）

## 6. 季度治理节奏

每季度第 1 个月内由架构组 + 标准组联合执行：

| 项 | 检查 | 输出 |
|---|---|---|
| STD 复核 | 9 份 STD 是否仍适用 / 是否需新增 | 季度治理报告 §STD |
| ADR 复盘 | 上季度 accepted ADR 是否兑现 / 是否需 supersede | 季度治理报告 §ADR |
| 红线扫描 | CI 红线告警统计（SSOT 复制 / VIEW 直写 schema / `_data-index.md` 被手改）| 红线 dashboard |
| `gate:waived` 滥用率 | 上季度 waived 笔数 / 总 gate 笔数；按团队 + step-id 切片 | 红线 dashboard |
| Debt review | `_facts/decisions-log` 中 W-NN 待建项进度 | 季度治理报告 §debt |

## 7. 自动化 hook 清单（CI 兜底）

| hook | 触发 | 工具 | 失败行为 |
|---|---|---|---|
| `build-data-index` | PR 改动 `apps/<svc>/migrations/**` | ✅ `scripts/build-data-index.py` | 自动 regen + 漂移即 fail |
| `contracts sync` | PR 改动 `apps/**` 或 `_registry.yaml` | ✅ `scripts/check-contracts-sync.py`（W16）| `_registry.services` ↔ `apps/svc-*/` parity + `events.publisher/subscribers` 必须已注册，任一不一致即 fail |
| `contracts drift` | PR 改动 `contracts/**` 或 `_registry.yaml` | ✅ `scripts/check-contracts-drift.py`（W15）| `_registry.contracts.{provides,consumes}` 路径必须存在 + 契约文件含 `openapi`/`asyncapi` 顶层字段，否则 fail |
| `role-badge lint` | 任何 PR 改 `docs/services/**` 或 `tech-standards/**` | (待建) | 首行缺 `<!-- ROLE: ... -->` 即 fail |
| `_data-index lint` | 任何 PR 改 `docs/services/<svc>/_data-index.md` | (内置) | 缺 `AUTO-GENERATED` 头即 fail |
| `spec HOW lint` | 任何 PR 改 `specs/**/spec.md` | ai-kit hooks | 出现库名/框架/数据结构关键词即 fail（详 playbook §3.1） |
| `verification: 字段` | 任何 PR 改 `specs/**/plan.md` | ai-kit hooks | 任一 task 缺 `verification:` 即 fail |
| `Closes #N` | commit-msg | ai-kit hooks | commit 缺 `Closes #N` 即 fail |

> 待建项进度见 `_facts/decisions-log` W-NN 表；季度治理报告统计完成率。
